> the Red **김태곤의 프론트엔드 back to the basics** 강의를 키워드 위주로 정리한 것이다. 다듬지 않은 문장이 많다. 개인적인 기록이 목적이고, 경험이 쌓이면 다시 쓸 생각이다.

## 프론트엔드란

- 애플리케이션이 사용자와 맞닿는 지점을 만드는 사람이다.
- 인터랙션을 정의하고 구현하는 일, 시각적인 완성도, 서버 통신, 그리고 그것을 쓰는 사용자까지 모두 고려해야 한다.
- 배포와 디자인에도 관여한다.
- 결국 **사용자**와 직접 연결된 분야다. 조작이 불편해선 안 된다.

공부할 것이 많다.

- 한 번 배우고 끝나는 영역이 아니다.
- 비즈니스 로직을 많이 다루게 되므로 백엔드 지식도 필요하다.
- 데이터베이스와 인증 정도를 빼면 점점 프론트로 넘어오는 추세다.

명세와 언어의 범위도 계속 움직인다.

- HTML5, CSS3 같은 통짜 버전은 이제 없다. HTML은 버전 없는 리빙 스탠다드가 됐고, CSS도 모듈별로 레벨이 올라간다.
- 자바스크립트는 웹 밖에서도 쓰이는 언어가 됐다.
- React Native로 네이티브 언어를 몰라도 어느 정도 네이티브 앱을 만들 수 있고, Electron으로 데스크톱 앱까지 웹 기술로 만든다.

트렌드가 자주 바뀐다.

- [깃허브 트렌딩](https://github.com/trending)을 자주 보고, 반복해서 눈에 띄는 것을 자세히 들여다본다.
- 메일링이나 트위터처럼 트렌드를 정리해 보내주는 것을 구독해둔다.
- 웬만하면 영어로 읽는다. 해외 트렌드에 민감할 필요가 있다.

## 공부 방법

- 영역은 넓혀가되, 필요한 부분은 깊게 판다.
- 이것저것 많이 경험해보는 것이 필요하다.
- 다른 사람의 코드를 많이 읽고, 개인 프로젝트를 한다.
- 시간을 들인 만큼 성장한다.

기술을 볼 때는 순서가 있다.

- 이 기술을 왜 만들었는지, 어떤 문제를 해결하려 했는지부터 본다.
- 쉬운 예제로 손을 움직여본다.
- 도저히 이해가 안 되면 개발자 커뮤니티에 묻는다.

### 개인 프로젝트

- 최신 버전이나 지금 인기 있는 기술을 써봐도 좋다. 실무에서 못 하는 걸 해보는 자리다.
- 아이디어는 자기에게 실제로 유용한 것에서 찾는다.
- 지금 가진 기술과 상관없이 아이디어부터 메모해두고, 나중에 맞는 기술을 붙여 진행한다.
- **문제를 직접 해결해보면 보는 눈이 달라진다.**

## 공식 문서

- 공식 문서를 잘 읽는다. 업데이트가 가장 빠르다.
- MDN을 읽는다.
- 자주 읽다 보면 몰랐던 것이 계속 나온다.
- [devdocs](https://devdocs.io/)는 여러 공식 문서 레퍼런스를 한곳에 모아둔 곳이다. 내려받아 오프라인으로도 쓸 수 있다.

## 블로그

개발 블로그를 쓴다.

- 나름의 목표를 정하고 팁을 올린다.
- 정확한 지식만 전달한다.
- 근거가 되는 자료를 첨부한다.
- 짧고 명료한 문장으로 쓴다.

- 설명하다 보면 자기 검증이 된다.
- 아주 짧은 책을 쓴다는 생각으로 기록한다.
- 예제 코드가 함께 있으면 좋다.
- 수식어는 적게 쓴다.

참고 — [개발자가 블로그를 운영해야 할 이유](https://taegon.kim/archives/7107)

## 개발 환경

- 여러 도구를 써보고 자신에게 맞는 것을 고른다.
- vi나 vim을 다룰 수 있어야 급할 때 쓸 수 있다.

### Git

- 저장소가 분리되어 있어 협업에 좋다. 다만 러닝 커브가 있다.
- 커밋 메시지를 잘 쓰는 방법을 알아둔다.
- 혼자 하는 프로젝트에서도 규칙을 지킨다.
- GUI만 쓰지 말고 CLI를 익혀둔다.

참고 — [좋은 git 커밋 메시지를 작성하기 위한 7가지 약속](https://meetup.toast.com/posts/106), [생활코딩 — 지옥에서 온 깃](https://opentutorials.org/course/2708), [팀 개발을 위한 깃](http://www.yes24.com/Product/Goods/85382769)

### 셸

- [oh-my-zsh](https://ohmyz.sh/)로 셸 환경을 만들면 여러 기능을 손쉽게 쓸 수 있다. iTerm도 쓰기 편하다.
- 맥에서 하기 어려운 IE 테스트는 [버추얼박스](https://www.virtualbox.org/)로 할 수 있다.
- 개인 프로젝트에서는 Node.js 최신 버전을 써본다. 버전을 갈아타며 테스트하려면 [nvm](https://github.com/nvm-sh/nvm)을 쓴다.

## 실무

- 노동 집약적이다.
- 결과물에 시각적인 요소가 많아 일정을 예측하기 어려운 면이 있다.

- 자주 쓰는 스타일은 컴포넌트로 만든다.
- 디자인팀과 합의한 컴포넌트를 기준으로 아토믹 디자인을 적용한다.

- MVP를 만든다. 꼭 필요한 부분만 만들어 피드백을 받는다.
- 최소 규모로 자주 반복한다.

- 백엔드와의 API 소통이 중요하다. 명세는 프론트에서 정의하는 편이 편하다.

- "안 된다"는 말은 되도록 아낀다.
- 조건이나 요구가 바뀌면서 일정을 조정하는 일이 종종 있다.

### 풀스택

- 진정한 의미의 풀스택이 있을까.
- 풀스택이 가능할 정도의 백엔드 지식은 있으면 좋다.
- 다만 한 분야에서 정진하는 편이 낫다.

## 정리

- 프론트엔드는 사용자와 맞닿아 있고, 그래서 범위가 계속 넓어진다
- 영역은 넓게, 필요한 곳은 깊게. 기술은 "왜 만들었는지"부터 본다
- 공식 문서와 개발 블로그는 둘 다 자기 검증 수단이다
- 실무에서는 최소 규모로 자주 반복하는 것이 예측 가능성을 만든다
