한컴 기술블로그의 [AI 시대에 테스트 코드를 잘 쓰는 기준이 달라진다](https://tech.hancom.com/test-code-in-ai-era/)(오진주, 2026-07-01)를 읽고 우리 레포에 적용한 기록이다. 원문은 Java/Spring 기준이라 옮기는 과정에서 바뀐 것이 꽤 있다.

AI가 놓치는 부분 없이 코드를 다 짜주는 상황이 되면서 테스트 코드의 의미에 대해 계속 고민했다. 회귀를 잡으려고 쓰는 거라면, 구현을 통째로 다시 만드는 게 더 빠른 경우도 있다. 원문은 그 질문에 다른 답을 준다. **테스트는 다음 세션의 AI가 읽는 명세**라는 것이다.

## 주석은 조용히 낡고 테스트는 깨진다

AI와 작업하면 세션이 끝날 때마다 맥락이 사라진다. 코드는 남지만 **왜 그렇게 했는지가 날아간다.** 다음 세션의 AI는 소스를 읽고 "지금 무슨 일이 일어나는가"만 알 수 있다.

이걸 주석으로 남기면 될 것 같지만, 주석은 코드가 바뀌어도 그대로 남아 있다. 틀린 채로 조용히 살아 있다. 반면 테스트는 코드와 어긋나는 순간 CI에서 깨진다. **동기화가 강제되는 유일한 문서**라는 게 원문의 핵심이다.

그래서 테스트를 보는 관점이 바뀐다. 안전망이 아니라 **결정을 옮기는 물건**이다.

## 타이틀에 Why를 적는다

관점이 바뀌면 제일 먼저 바뀌는 건 `it` 타이틀이다. 본문이 사라져도 타이틀만 읽고 "이 코드가 어떤 정책을 지키는지"를 알 수 있어야 한다.

```ts
// 나쁜 예 — 기계적 서술. 정책이 없다
it("hide를 호출하면 isVisible이 false가 된다", () => {});
it("localStorage에 값을 저장한다", () => {});
it("null이면 null을 반환한다", () => {});
```

이 타이틀들은 구현을 그대로 다시 쓴 것이다. 코드를 읽으면 알 수 있는 내용이라 새로 알려주는 게 없다.

```ts
// 좋은 예 — 비즈니스 목적과 경계가 보인다
it("'그만보기'를 누른 뒤에는 재노출을 멈춰 사용자 피로도를 낮춘다", () => {});
it("스키마와 다른 스토리지 값은 정보 노출·오작동 방지를 위해 null로 폴백한다", () => {});
it("딥링크 어트리뷰션 키는 로그아웃 clear에도 보존해 마케팅 성과 유실을 막는다", () => {});
```

세 번째가 특히 그렇다. "로그아웃할 때 이 키는 지우지 않는다"는 코드만 보면 버그처럼 보인다. 타이틀이 없으면 다음 사람이 정리하다가 지운다.

## 모든 테스트에 Why가 있는 건 아니다

규칙으로 옮기려는데 여기서 한 번 걸렸다. **비즈니스 맥락을 담은 테스트와 단순 구현 검증 테스트는 목적이 다르다.** 이걸 구분하지 않으면 규칙을 잘못 만들게 된다.

`cn`이나 `formatNumber` 같은 순수 유틸리티에는 비즈니스 Why가 **존재하지 않는다.** 거기에 Why를 요구하면 없는 걸 만들어내게 된다. 그리고 이 패러다임이 가장 잘 맞는 곳은 반대쪽 — `section`/`screen`/`page` 단위의 통합 테스트다.

그래서 두 종류로 갈랐다. 계층이 아니라 **목적**으로 나눈 것이다.

| | 의도 테스트 | 구현 검증 테스트 |
| --- | --- | --- |
| 대상 | 도메인 로직 — 훅, 서비스, 특히 `section`·`screen`·`page` 통합 | 순수 유틸, 포매팅 |
| 타이틀 | 정책과 그 이유 | 기술적 계약을 그대로 |
| 예시 | `'그만보기'를 누른 뒤에는 재노출을 멈춰 사용자 피로도를 낮춘다` | `중복 클래스는 뒤 값이 이긴다` |

섞지 않는 것이 규칙이다. **구현 검증 테스트에 가짜 Why를 붙이지 않고, 정책을 기계적 단언으로 낮추지도 않는다.**

## AI가 Why를 지어내지 않게

적용하면서 가장 신경 쓴 부분이다. Why를 타이틀에 넣으라고 하면 AI는 맥락이 없어도 넣는다. 코드 동작을 보고 그럴듯한 이유를 **추론해서** 쓴다.

이게 위험한 이유는 결과물이 멀쩡해 보인다는 것이다. 그럴듯하지만 틀린 Why는 CI를 통과한다. 뒤에 나올 역추론 검증까지 통과한다. 앞뒤가 맞기 때문이다. 그리고 한번 들어가면 그게 정책의 근거가 된다.

그래서 규칙을 이렇게 뒤집었다. **맥락이 주어지지 않으면 추론하지 않는다.**

- 사용자가 정책을 주지 않았으면 코드에서 유추하지 말고 기획·티켓에서 확인하거나 사람에게 묻는다
- 확인되기 전까지는 중립적인 기술 계약 타이틀로 쓰고, `// TODO(intent): 근거 미확인` 마커를 남긴다

검증되지 않은 근거가 단일 원천에 들어가는 것보다, 비어 있는 자리가 눈에 보이는 편이 낫다.

## 타이틀부터 합의하고 본문은 나중에

원문이 제안하는 spec-first 워크플로를 그대로 가져왔다. 사람이 명세를 먼저 정하고 AI가 구현만 채우는 순서다.

**1단계 — 타이틀만 합의한다.** 본문은 비워 둔다.

```ts
describe("useModalExposure", () => {
  it("첫 노출 사용자는 모달을 볼 수 있어야 한다 (유입 기회 보장)");
  it("이미 '오늘 그만보기'를 누른 사용자에게는 재노출하지 않는다 (피로도 관리)");
  it("노출 기간(start~end)을 벗어나면 캠페인을 숨긴다 (운영 정책)");
});
```

이 상태는 합의를 위한 스케치이고 실행할 것이 아니다. 실제로 돌리면 Jest가 예외를 던진다.

```text
Missing second argument. It must be a callback function.
Perhaps you want to use `test.todo` for a test placeholder.
```

플레이스홀더를 실행까지 시키고 싶으면 `it.todo("…")`를 쓴다. 그러면 통과가 아니라 todo로 집계돼서, 합의만 되고 구현되지 않은 명세가 초록색에 섞이지 않는다.

**2단계 — 확정된 타이틀 안을 given/when/then으로 채운다.**

```ts
it("이미 '오늘 그만보기'를 누른 사용자에게는 재노출하지 않는다 (피로도 관리)", () => {
  // given: 내일 0시까지 숨김 날짜가 저장된 상태
  const future = new Date(Date.now() + 86_400_000).toISOString();
  localStorage.setItem(
    "modalExposureStates",
    JSON.stringify({ [TEST_KEY]: future }),
  );
  // when: 모달 노출 여부를 계산하면
  const { result } = renderHook(() => useModalExposure({ key: TEST_KEY }));
  // then: 숨김 상태를 유지한다
  expect(result.current.isVisible).toBe(false);
});
```

given/when/then을 주석으로 강제한 게 의외로 효과가 있었다. **어떤 상황에서, 언제 쓰고, 어떤 결과가 나오는지**가 세 줄로 분리되니 타이틀의 정책이 본문에서 실제로 검증되는지 눈으로 확인된다.

## 거부는 skip하지 말고 단언한다

정책이 거부해야 하는 입력이 있으면 `it.skip`으로 넘기지 않는다. **거부하는 동작 자체가 지켜야 할 명세**다.

```ts
// 나쁜 예 — skip은 정책을 침묵시킨다
it.skip("잘못된 값이 저장돼 있으면 무시한다", () => {});
```

왜 스킵했는지, 무엇을 거부해야 하는지 아무 정보가 없다. 다음 사람은 이게 미완성인지 의도적인지 알 수 없다.

```ts
// 좋은 예 — 거부와 폴백을 명시적으로 단언한다
it("스키마에 맞지 않는 저장 값은 신뢰하지 않고 null로 폴백한다 (오염 데이터 차단)", () => {
  // given: 스키마에 위배되는 값이 저장된 상태
  localStorage.setItem("modalExposureStates", JSON.stringify({ key: 123 }));
  // when: 값을 읽으면
  const value = localStorageService.getItem("modalExposureStates");
  // then: 오염된 값을 반환하지 않고 null로 폴백한다
  expect(value).toBeNull();
});
```

## 의도가 실제로 전달되는지 확인한다

이 방식은 의도가 정말 살아남을 때만 작동한다. 그래서 확인 절차를 두 개 뒀다. 원문의 제안을 그대로 쓴 부분이다.

- **교차 검토** — 타이틀을 **다른 모델**에게 읽히고 리뷰를 받는다. 같은 세션의 AI는 자기가 쓴 것을 합리화한다
- **역추론** — 본문을 가리고 타이틀만 AI에게 주고 비즈니스 규칙을 복원하게 한다. 복원이 안 되면 타이틀이 아직 의도를 담고 있지 않은 것이니 다시 쓴다

역추론은 값이 확실한데 한 가지 함정이 있다. 앞서 말한 **지어낸 Why도 이 검증을 통과한다.** 앞뒤가 맞게 지어냈기 때문이다. 그래서 역추론은 "타이틀이 읽히는가"만 검증하고, "그 근거가 사실인가"는 사람이 확인해야 한다. 두 검증을 같은 것으로 착각하면 안 된다.

## 문서로만 두면 안 쓰인다

여기까지 정리해서 `AGENTS.md`에 넣었다. 그런데 규칙 문서에 항목을 추가하는 것만으로는 실제로 지켜지지 않는다. 매번 "그 규칙대로 해줘"라고 말해야 하는 것은 결국 안 하게 된다.

그래서 `/test` 슬래시 커맨드로 만들었다. 대상 파일만 주면 다음 순서로 돈다.

1. 대상과 주변 코드를 읽는다
2. **두 종류 중 어느 것인지 분류한다**
3. 구현 검증 테스트면 바로 구현으로 간다
4. 의도 테스트면 **정책·허용 경계·거부 케이스를 먼저 확보한다.** 사용자가 안 줬으면 추론하지 말고 묻고 기다린다
5. 타이틀만 제안하고 **승인을 받는다.** 승인 전에는 본문을 쓰지 않는다
6. 해당 범위의 최소 게이트를 돌리고 결과를 그대로 보고한다

호출은 이렇게 한다. 맥락이 있는 경우와 없는 경우다.

```text
/test apps/web/lib/util/is-civil-adult.ts
종류: 의도 테스트
정책: 민법상 성년(만 19세 이상)만 true. 미성년 보호가 목적.
허용 경계: 만 19세가 되는 날 당일부터 true.
거부 케이스: birthDate 형식이 잘못되면(NaN) 성인 아님 → false로 안전 폴백.
```

```text
/test apps/web/lib/util/formatter.ts
```

두 번째처럼 맥락이 없으면 구현 검증 테스트로 판단해 그대로 진행한다. 첫 번째처럼 맥락이 있으면 AI가 파악한 것이 맞는지 승인하는 절차를 거친다.

**5번의 승인 게이트가 이 커맨드의 핵심이다.** 타이틀은 명세이고, 명세는 사람이 정해야 한다. 승인을 자유 입력이 아니라 버튼으로 받게 한 것도 의도적이다. 그냥 물으면 "네"라고 답하고 넘어가는데, 선택지를 제시하면 한 번은 읽는다.

## 어디까지만 하는가

원문도 한계를 짚고 있고, 적용하면서 같은 곳에 도달했다.

**과잉 명세는 테스트를 부러지게 한다.** 테스트는 **규칙이 어떻게 동작하는지**를 담는 것이고, **기능이 왜 존재하는지**는 티켓이나 ADR의 몫이다. 내부 구현까지 명세로 박아두면 리팩터링마다 테스트가 깨진다.

**낡은 테스트는 더 나쁘다.** 정책이 바뀌었는데 테스트가 그대로 통과하고 있으면, 그건 폐기된 정책을 조용히 단언하고 있는 것이다. 단일 원천으로 삼기로 했으면 갱신하거나 지워야 한다. 남겨두는 선택은 없다.

그래서 이 패러다임을 모든 테스트에 적용하지 않았다. **필요한 테스트에만 적용하고, 판단은 작성자에게 맡긴다.**

## 정리

- 테스트는 코드와 어긋나면 CI에서 깨진다. **동기화가 강제되는 유일한 문서**라서 세션 사이에 의도를 옮길 수 있다
- `it` 타이틀에 정책과 그 이유를 적는다. 본문이 사라져도 타이틀만으로 명세가 읽혀야 한다
- **모든 테스트에 Why가 있는 건 아니다.** 의도 테스트와 구현 검증 테스트를 목적으로 갈라 두고 섞지 않는다
- **AI가 Why를 지어내지 않게 막는 것이 가장 중요하다.** 그럴듯하지만 틀린 근거는 CI도 역추론 검증도 통과한다. 맥락이 없으면 추론하지 말고 물어야 한다
- 타이틀을 먼저 합의하고 본문을 given/when/then으로 채운다. 거부 케이스는 `it.skip`이 아니라 단언한다
- 규칙 문서에 적는 것만으로는 지켜지지 않는다. **승인 게이트가 있는 커맨드로 만들어야** 실제로 돈다
- 과잉 명세와 낡은 테스트는 이 방식의 대가다. 필요한 곳에만 적용한다
