같은 두 함수를 순서만 바꿔 썼는데 결과가 달랐다.

```html
<div class="rotate-translate">Rotated + Translated</div>
<div class="translate-rotate">Translated + Rotated</div>
```

```css
.rotate-translate {
  background-color: pink;
  transform: rotate(45deg) translateX(180px);
}

.translate-rotate {
  background-color: gold;
  transform: translateX(180px) rotate(45deg);
}
```

기울기는 둘 다 45도로 같다. 다른 것은 **어디로 갔는지**다. `rotate`를 먼저 쓴 분홍 상자는 대각선 아래로 갔고, `translateX`를 먼저 쓴 금색 상자는 수평으로 갔다.

## 순서는 왼쪽에서 오른쪽으로 적용된다

`transform`에 여러 함수를 적으면 왼쪽부터 차례로 적용된다. 이때 각 함수는 **앞선 변환이 만들어둔 좌표계 안에서** 동작한다. 그래서 앞의 변환이 뒤의 변환이 의미하는 방향을 바꿔버린다.

**`rotate(45deg) translateX(180px)`**

1. 먼저 요소를 45도 회전시킨다.
2. 그 다음 **회전된 축을 기준으로** X축 방향으로 180px 이동한다. 축이 이미 45도 기울어져 있으므로 이 "오른쪽"은 화면의 오른쪽 아래다.
3. 결과적으로 요소는 대각선 방향으로 이동한다.

**`translateX(180px) rotate(45deg)`**

1. 먼저 요소를 X축 방향으로 180px 이동시킨다. 아직 회전이 없으므로 화면 그대로의 오른쪽이다.
2. 그 다음 이동된 위치에서 45도 회전한다.
3. 결과적으로 요소는 수평으로 이동한 뒤 제자리에서 회전한다.

회전의 기준점은 `transform-origin`이고 기본값은 요소의 중심(`50% 50%`)이다. 위 그림도 그 기준이다.

### "오른쪽에서 왼쪽"이라는 설명도 보인다

같은 현상을 반대로 설명하는 글도 있다. 둘 다 틀린 말은 아니고, 무엇을 기준으로 보는지가 다르다.

- **좌표계를 기준으로** 보면 왼쪽 함수가 먼저 적용되고, 오른쪽 함수는 그렇게 바뀐 좌표계에서 동작한다.
- **점의 좌표를 기준으로** 보면 최종 좌표는 `p' = A · B · C · p`로 계산되므로, 가장 오른쪽 함수가 점에 먼저 닿는다.

코드를 읽으면서 결과를 머릿속에 그릴 때는 앞의 관점이 편하다. 왼쪽부터 순서대로 따라가면 된다.

## 행렬로 보면

각 변환은 행렬로 표현되고, 여러 변환을 적용하면 이 행렬들이 곱해진다. 행렬 곱셈은 교환법칙이 성립하지 않으므로 곱하는 순서에 따라 결과가 달라진다.

위 두 선언을 행렬로 계산하면 이렇게 된다.

```css
/* rotate(45deg) translateX(180px) */
transform: matrix(0.707, 0.707, -0.707, 0.707, 127.279, 127.279);

/* translateX(180px) rotate(45deg) */
transform: matrix(0.707, 0.707, -0.707, 0.707, 180, 0);
```

앞의 네 값(회전·확대 성분)은 같고 뒤의 두 값(이동 성분)만 다르다. 그림에서 기울기는 같고 위치만 달랐던 것이 그대로 숫자로 나타난다.

다만 **언제나** 순서가 중요한 것은 아니다. 실제로는 성립하는 조합도 있다.

| 조합 | 순서를 바꾸면 |
| --- | --- |
| `rotate(45deg) scale(2)` | 같다 |
| `translateX(10px) translateY(20px)` | 같다 |
| `rotate(45deg) translateX(10px)` | 다르다 |

회전과 확대는 둘 다 원점을 기준으로 하니 순서를 바꿔도 같고, 이동끼리도 더하는 것이라 같다. 어긋나는 것은 **이동과 회전·확대가 섞일 때**다. 이동은 좌표계를 옮기고, 회전과 확대는 원점을 기준으로 하기 때문이다.

## 성능과는 상관이 없다

`transform`의 순서가 성능에 영향을 준다는 이야기를 종종 보는데, 그렇지 않다.

**순서는 성능 다이얼이 아니라 결과를 바꾸는 것이다.** 위에서 본 대로 순서가 다르면 행렬이 다르다. 성능을 위해 `translate` → `rotate` → `scale` 순으로 재배열하면 화면이 달라진다. 애초에 자유롭게 바꿀 수 있는 것이 아니다. 브라우저는 어떤 순서든 하나의 행렬로 합성하고, 그 합성 비용은 순서와 무관하다.

`transform`의 실제 이점은 순서가 아니라 **레이아웃을 트리거하지 않는다**는 데 있다. `left`나 `top`을 애니메이션하면 매 프레임 레이아웃이 다시 계산되지만, `transform`은 그 단계를 건너뛴다. 그래서 위치를 움직이는 애니메이션은 `transform`으로 하는 것이 좋다.

### 레이어 승격

한 걸음 더 나가려면 요소를 별도의 합성 레이어로 올릴 수 있다. 두 가지 방법이 있다.

```css
/* 예전부터 쓰인 방법 */
transform: translate3d(0, 0, 0);

/* 의도를 그대로 적는 방법 */
will-change: transform;
```

`translate3d(0, 0, 0)`는 실제로 요소를 움직이지 않지만 3D 변환을 쓰는 것만으로 레이어 승격을 유도한다. 오래 쓰인 관용구이고 넓게 동작하지만, 코드만 봐서는 의도가 드러나지 않는다.

`will-change`는 "이 속성이 곧 바뀔 것"이라고 브라우저에 미리 알린다. 하는 일이 이름에 적혀 있으니 이쪽이 낫다.

어느 쪽이든 **필요할 때만** 쓴다. 레이어마다 메모리를 쓰기 때문에 남발하면 오히려 느려진다. `will-change`는 변화가 예상되기 직전에 붙이고 끝나면 떼는 것이 좋고, 붙이기 전과 후를 실제로 측정해서 나아졌는지 확인해야 한다.

## matrix() 대신 개별 함수로

`matrix()`는 여섯 개 숫자로 같은 변환을 한 번에 적을 수 있다. 하지만 이걸 보고 무슨 변환인지 알아내려면 계산을 해야 한다.

```css
/* 무슨 변환인가? */
transform: matrix(0.707, 0.707, -0.707, 0.707, 180, 0);

/* 읽으면 알 수 있다 */
transform: translateX(180px) rotate(45deg);
```

결과는 같다. 성능 차이도 없다. 개별 함수로 적는 것은 읽는 사람을 위한 선택이다.

## 정리

- `transform`의 함수는 왼쪽부터 적용되고, 각 함수는 앞선 변환이 만든 좌표계 안에서 동작한다
- 그래서 `rotate` 다음의 `translateX`는 기울어진 축을 따라 움직인다
- 이동과 회전·확대가 섞이면 순서가 결과를 바꾼다. 회전과 확대끼리, 이동과 이동끼리는 순서를 바꿔도 같다
- **순서와 성능은 상관이 없다.** `transform`의 이점은 레이아웃을 트리거하지 않는다는 것이다
- 레이어 승격은 `translate3d(0,0,0)`보다 `will-change`가 의도가 분명하다. 둘 다 필요할 때만, 측정해보고 쓴다
- `matrix()`보다 개별 함수가 읽기 쉽다
