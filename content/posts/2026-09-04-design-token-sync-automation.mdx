디자인팀이 Figma에서 토큰을 내보내 Notion에 올리면 개발자가 받아 수동으로 반영했다. 노티 확인 → 브랜치 → 파일 교체 → 산출물 재생성 → 검수 → PR → 수정, 일곱 단계다. 짧게 한 시간, 다른 일로 바쁘면 며칠이 걸렸다.

병목은 작업량이 아니었다. **사람이 시간을 낼 수 있는지**였다. 한 시간짜리 일이 며칠 걸리는 건 그 한 시간을 언제 내는지의 문제다.

## 제약부터

가장 곧은 길은 Figma에서 직접 읽어오는 것이다. 그런데 **Figma Variables REST API는 Enterprise 플랜 전용**이다. 쓰려면 조직 플랜을 올려야 했다.

비용을 요구하기 전에 업그레이드 없이 되는 경로를 먼저 찾기로 했다. 안 된다는 걸 증명한 뒤에 돈을 얘기하는 게 순서라고 봤다.

남은 재료는 이미 있는 것들이었다. 디자인팀은 이미 Notion에 토큰 JSON을 올리고 있었다. 그 흐름을 바꾸지 않고 **기계가 읽을 수 있게만** 만들면 됐다.

## 큐는 상태 속성 하나다

Notion 데이터베이스에 토큰 JSON을 첨부하는 행이 있고, 거기에 `상태` 속성이 있다. 값이 두 개다.

- `토큰이 변경됐어요` — 디자인팀이 올리고 이렇게 바꾼다
- `업데이트 완료` — 코드에 반영되면 되돌아간다

동기화 스크립트는 **상태가 `토큰이 변경됐어요`인 행만** 가져온다. 이게 큐다. 별도 시스템이 없다. 디자인팀이 하던 일은 그대로고, 상태를 바꾸는 동작 하나가 "처리해달라"는 신호가 된다.

```ts
const rows = await fetchTokenRows({
  databaseId,
  onlyChanged: values.all !== true,
});

if (rows.length === 0) {
  console.log("가져올 토큰이 없습니다. (상태가 '토큰이 변경됐어요' 인 행 없음)");
  return;
}
```

`--all`을 주면 상태를 무시하고 전체를 다시 받는다. 큐가 비어 있어도 강제로 재수신해야 하는 경우가 있어서 남겼다.

## 외부 응답을 믿지 않는다

Notion API 응답은 남이 만든 데이터다. 첨부 파일 이름도 사람이 올린 것이다. 두 군데서 막았다.

**파일 이름 화이트리스트.** 산출물 생성 스크립트가 읽는 파일은 열한 개로 정해져 있다. 목록에 없는 이름이 오면 무시하고 경고만 남긴다.

```ts
const KNOWN_TOKEN_FILE_NAMES = new Set([
  "primitives.json",
  "semantic.light.json", "semantic.dark.json",
  "component.light.json", "component.dark.json",
  "shadow.light.json", "shadow.dark.json",
  "typography.json", "spacing.json", "radius.json", "border.json",
]);
```

이게 없으면 누가 엉뚱한 파일을 첨부했을 때 그 이름으로 파일이 생긴다. 경로 문제는 물론이고, 산출물 생성이 읽지 않는 파일이 저장소에 조용히 쌓인다.

**받은 내용이 JSON인지 확인한다.** 첨부가 깨졌거나 HTML 에러 페이지가 내려오는 경우가 있다.

```ts
try {
  JSON.parse(content);
} catch {
  throw new Error(`${file.name} 이 올바른 JSON 이 아닙니다. Notion 첨부를 확인하세요.`);
}
```

파싱 실패는 경고가 아니라 중단이다. 깨진 파일을 커밋하면 그 뒤 단계가 전부 무의미해진다.

## 워크플로 세 개로 루프를 닫는다

| 워크플로 | 언제 | 하는 일 |
| --- | --- | --- |
| **Sync** | 평일 10시 + 수동 실행 | Notion에서 받아 반영, 산출물 재생성, PR 생성, Slack 알림 |
| **Check** | 토큰 경로가 바뀐 PR | 산출물 동기화 검증, 삭제 토큰 사용처 검사, 변경 리포트 코멘트 |
| **Synced** | 라벨 붙은 PR이 머지될 때 | Notion 상태를 `업데이트 완료`로 되돌리고 날짜 기록 |

세 번째가 있어서 루프가 닫힌다. 이게 없으면 디자인팀은 자기가 올린 게 반영됐는지 물어봐야 한다. 상태가 되돌아가는 것이 대답이다.

사람에게 남은 것은 **리뷰와 머지**뿐이다. 앞의 다섯 단계가 워크플로 안에서 끝난다.

## 포매팅 소음이 두 종류 나온다

자동화하고 나서 예상하지 못한 문제가 이쪽이었다.

**첫째, 토큰 JSON 자체의 포매팅.** Notion에서 내려받은 파일을 그대로 쓰면 값은 그대로인데 들여쓰기나 줄바꿈만 다른 diff가 생긴다. 산출물 재생성 뒤에 토큰 JSON까지 Prettier로 정규화했다.

```yaml
- name: 테마 재생성
  run: |
    pnpm --filter @repo/ui generate-theme
    pnpm exec prettier --write --log-level warn \
      "packages/ui/tokens/*.json" \
      packages/ui/src/styles/theme.css \
      packages/ui/src/styles/shadow.css \
      packages/ui/src/stories/color-tokens.json
```

이걸로 **포매팅 차이 8건이 걸러지고 실제 변경 3건만** 리뷰 대상으로 남았다. 리뷰어가 열한 개 파일을 훑으며 어디가 진짜 바뀐 건지 찾지 않아도 된다.

**둘째, 클래스 정렬 순서가 바뀐다.** 이건 훨씬 덜 직관적이다. `prettier-plugin-tailwindcss`는 Tailwind가 아는 유틸리티를 정해진 순서로 정렬하고 모르는 클래스는 앞에 놓는다. 그런데 **토큰 이름이 바뀌면 아는 클래스와 모르는 클래스의 경계가 움직인다.** 그러면 토큰과 아무 상관없는 파일 수십 개에서 클래스 순서가 달라지고, 포맷 검사 게이트가 그 파일들을 전부 실패로 잡는다.

```yaml
# 토큰 이름이 바뀌면 prettier-plugin-tailwindcss 가 매기는 클래스 정렬 순서도 바뀐다.
# 여기서 저장소 전체를 다시 정렬해 두지 않으면 토큰과 무관한 파일 수십 개가
# quality 게이트에서 포맷 실패로 잡힌다.
- name: Tailwind 클래스 재정렬
  run: pnpm exec prettier --write --log-level warn "**/*.{ts,tsx,md}"
```

토큰 리네임의 파급이 CSS에서 끝나지 않고 **포매터를 거쳐 관계없는 파일까지 번진다.** 자동화하기 전에는 사람이 그때그때 포맷을 맞춰서 이런 게 보이지 않았다.

## 리뷰어에게 영향 범위를 준다

토큰이 삭제되거나 이름이 바뀌면 그걸 쓰던 코드가 깨진다. [앞 글](/blog/tailwind-token-silent-failure)에서 다룬 대로 이건 CI에서 따로 잡아야 한다.

Sync 워크플로는 PR을 만들면서 **그 가드를 미리 돌려 결과를 PR 본문에 실어 준다.** PR을 받은 사람이 CI 실패 로그를 열지 않아도 고칠 곳을 바로 안다. 변경 리포트에는 삭제된 토큰의 사용처 수까지 들어간다.

가드가 실패해도 동기화를 막지는 않는다. 토큰 반영과 사용처 수정은 같은 PR에서 이어서 하면 되고, 어차피 머지 전에 Check 워크플로가 잡는다. 여기서 막으면 PR 자체가 안 만들어져서 디자인팀 쪽 상태도 안 움직인다.

## 없으면 조용히 건너뛴다

시크릿이 없을 때의 동작을 정해둬야 했다. 두 경우가 다르다.

- **Notion 토큰이 없으면** Sync 워크플로는 실패하지 않고 notice만 남기고 건너뛴다. 이 워크플로는 정기 실행이라, 시크릿이 없는 포크나 초기 설정 중에 매일 빨간 실패가 쌓이면 아무도 안 보게 된다
- **Slack 토큰이 없으면** 알림 스텝만 건너뛰고 PR은 정상적으로 열린다. 알림은 부수적이고 PR이 본체다

실패시킬 것과 건너뛸 것을 가르는 기준은 "이게 없으면 결과물이 틀리는가"였다. 알림이 안 가도 PR은 맞고, 토큰을 못 받으면 애초에 할 일이 없다.

## 정리

- 유료 플랜이 전제인 API는 **비용을 요구하기 전에 우회 경로를 먼저 증명**했다. Figma Variables API는 Enterprise 전용이다
- 디자인팀이 이미 쓰던 Notion 흐름을 바꾸지 않고, **상태 속성 하나를 큐로** 썼다. 사람의 일은 그대로고 검증만 끼워 넣었다
- 외부 응답은 파일 이름 화이트리스트와 JSON 파싱으로 좁혀서 받는다
- 워크플로 세 개(Sync·Check·Synced)로 **루프를 닫는다.** 상태가 되돌아가는 것이 디자인팀에 대한 대답이다
- 토큰 리네임은 CSS에서 끝나지 않는다. **포매터의 클래스 정렬 순서까지 흔들려** 무관한 파일이 포맷 게이트에 걸린다
- 시크릿이 없을 때 실패시킬지 건너뛸지는 "없으면 결과물이 틀리는가"로 갈랐다
