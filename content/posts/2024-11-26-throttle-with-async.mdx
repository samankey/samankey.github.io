앱에 요일별로 일감 리스트를 볼 수 있는 페이지가 있다. 이슈가 있어 확인해보니 이런 상태였다.

**정상 동작이라면** — 요일 필터를 누르면 해당 요일에 일감 데이터가 있으면 리스트를 렌더링하고, 없으면 `EmptyItem` 컴포넌트를 렌더링한다.

**이슈** — 데이터가 있어도 `EmptyItem`이 잠시 떴다가 리스트가 렌더링된다.

원인은 비동기 작업과 throttle을 함께 쓴 데 있었다.

## 문제가 된 코드

`getWorkList`는 lodash `throttle`로 감싼 async 함수다. `init`이 참이면 먼저 `workList`를 비운다.

```js
getWorkList: _.throttle(async function (loading, workType, init = false) {
  if (init) {
    this.initWorkList();  // workList 배열을 비운다
  }
  this.workList = await ... // 비동기 작업 수행
}, 1000)
```

요일이 바뀌면 `watch`가 `refreshHandler`를 트리거한다.

```js
// 이 함수로 selectDate가 변경됨
selectDateAction(date) {
  this.selectDate = date;
  this.aroundWorkListLog('date');
},

// watch에서 감지하고 있는 selectDate가 refreshHandler 트리깅
async selectDate(n, o) {
  // 단기 날짜 필터 변경시
  if (n !== o && this.loadDone && this.isShort) {
    this.refreshHandler(true, true, true);
  }
}

async refreshHandler(changeLoad = false, loading = false, scrollTop = false) {
  try {
    if (changeLoad) this.loadDone = false;
    // ... 기타 작업
    await this.getWorkList(false, this.workType, true);
  } catch (e) {
    this.ajaxError(e);
  } finally {
    if (changeLoad) this.loadDone = true;
    // ... 기타 작업
  }
}
```

그리고 `EmptyItem`의 표시 여부는 이렇게 결정된다.

```vue
<EmptyItem
  v-if="loadDone && !workList.length"
  ...
/>
```

## throttle은 억제한 호출을 버리지 않는다

여기서 두 가지가 겹친다. 둘 다 lodash `throttle`이 억제한 호출을 어떻게 다루는지에서 나온다.

### 억제된 호출은 이전 호출의 Promise를 돌려준다

throttle된 함수를 창(window) 안에서 다시 부르면, 새 호출이 실행되지 않는 건 알고 있었다. 그런데 **반환값이 `undefined`가 아니다.** 직전에 실제로 실행된 호출의 반환값을 그대로 돌려준다.

async 함수라면 그 반환값은 Promise다. 즉 억제된 호출에서 받는 것은 **이전 호출의 Promise**이고, 그것은 이미 resolve되어 있을 수 있다.

```js
const f = _.throttle(async function (tag) { /* 300ms 걸리는 작업 */ }, 1000);

const pA = f('A');   // 실제로 실행됨
const pB = f('B');   // 억제됨
pA === pB;           // true
```

그래서 `await this.getWorkList(...)`는 "이 호출이 끝날 때까지"를 뜻하지 않는다. 억제된 호출에서는 이미 끝난 작업을 기다리게 되고, `await`이 즉시 통과한다. `finally`의 `loadDone = true`도 함께 즉시 실행된다.

`leading: false`로 두면 아직 실행된 적이 없어 `undefined`가 돌아오고, `await undefined`는 더 빨리 통과한다.

### 억제해둔 호출은 창이 끝날 때 혼자 실행된다

throttle은 억제한 호출을 버리지 않는다. 창이 끝나는 시점에 마지막 인자로 한 번 실행한다. 이때는 **아무도 그 호출을 `await`하고 있지 않다.** `refreshHandler`는 한참 전에 끝났고 `loadDone`은 이미 `true`다.

그 상태에서 뒤늦은 호출이 `initWorkList()`로 `workList`를 비운다. `loadDone && !workList.length`가 성립한다.

## 재현

같은 구조로 화요일을 누르고 400ms 뒤에 수요일을 눌러봤다. `fetch`는 300ms, throttle 창은 1000ms다.

```text
   0ms  TAP 화  (loadDone=true)
   1ms  getWorkList INVOKED (selectDate=화, init=true)
   1ms  initWorkList()  -> workList=[]
 302ms  fetch done -> workList=2건
 302ms  finally: loadDone=true   [workList=2, EmptyItem=안 보임]

 401ms  TAP 수  (loadDone=true)
 402ms  finally: loadDone=true   [workList=2, EmptyItem=안 보임]
1001ms  getWorkList INVOKED (selectDate=수, init=true)
1002ms  initWorkList()  -> workList=[]
1012ms  >>> EmptyItem 보임
1302ms  fetch done -> workList=2건
1309ms  >>> EmptyItem 사라짐
```

401ms의 탭을 보면 `finally`가 1ms 뒤에 실행된다. `loadDone`이 false로 갔다가 곧바로 true로 돌아온다 — 이 탭에 대한 로딩 상태는 사실상 없었다.

그리고 1001ms에 억제해둔 호출이 실행되면서 리스트를 비운다. `EmptyItem`이 뜨고, 300ms 뒤 데이터가 도착하면 사라진다. **플래시가 지속되는 시간은 `fetch` 시간과 같고, 시작은 탭 후 창 하나만큼 뒤다.**

최종 데이터는 맞게 나온다. lodash가 뒤늦은 실행에 가장 최신 인자를 쓰고 `this.selectDate`도 최신 값을 읽기 때문이다. 깨진 것은 데이터가 아니라 UI 상태뿐이었고, 그래서 "데이터가 안 나온다"가 아니라 "잠깐 빈 화면이 뜬다"로 보였다.

## 어떻게 고쳤나

### 리스트를 미리 비우지 않는다

`init` 분기와 `initWorkList()` 호출을 없앴다. `this.workList = await ...`가 이미 배열을 통째로 교체하므로, 미리 비우는 단계는 원래 필요하지 않았다.

비우는 순간이 없어지면 `!workList.length`가 참이 되는 창도 없어진다. 뒤늦은 호출이 실행되더라도 화면에는 이전 데이터가 남아 있고, 새 데이터가 도착하면 교체된다.

### 최신 요청만 반영한다

요청마다 번호를 매기고, 응답이 돌아왔을 때 자기가 최신이 아니면 버린다. `loadDone`도 같은 번호로 막아서, 최신 요청이 끝났을 때만 로딩이 끝난 것으로 본다.

```js
async refreshHandler(changeLoad = false, loading = false, scrollTop = false) {
  const id = ++this.requestId;

  try {
    if (changeLoad) this.loadDone = false;
    await this.getWorkList(false, this.workType);
  } catch (e) {
    this.ajaxError(e);
  } finally {
    // 이 요청이 아직 최신일 때만 로딩을 끝낸 것으로 본다
    if (changeLoad && id === this.requestId) this.loadDone = true;
  }
}
```

이 가드가 없으면 먼저 시작한 느린 요청이 나중에 도착해서 최신 데이터를 덮어쓴다. 같은 뿌리에서 나오는 다른 증상이라 함께 막았다.

## 남겨둔 것

throttle은 `getWorkList`에 그대로 두었다. 그래서 억제된 호출에서 `await`이 이 호출의 완료를 뜻하지 않는다는 사실 자체는 남아 있다. 다만 그 사실에 기대는 코드가 없어졌다.

원인을 완전히 없애려면 async 함수에서 throttle을 떼고, 억제는 탭 핸들러 쪽에서 하는 편이 맞다. 요일 필터처럼 마지막 입력 하나만 반영하면 되는 경우에는 throttle보다 debounce가 어울린다. throttle의 "억제해둔 호출을 나중에 한 번 실행한다"는 성질이 여기서는 도움이 되지 않는다.

`v-if="loadDone && !workList.length"`도 약한 조건이다. `loadDone`은 "지금 로딩 중이 아니다"만 말하고 "한 번이라도 로드에 성공했다"는 말하지 않는다. 초기 상태, 로드 실패, 진짜 빈 결과가 모두 같은 화면이 된다.

## 정리

- lodash `throttle`이 억제한 호출은 `undefined`를 돌려주지 않는다. **직전에 실행된 호출의 반환값**을 돌려준다 — async 함수라면 이미 끝났을 수 있는 Promise다
- 그래서 throttle된 async 함수를 `await`하는 것은 이 호출의 완료를 기다리는 것이 아니다
- 억제한 호출은 버려지지 않고 창이 끝날 때 실행된다. 그때는 아무도 기다리지 않으므로, 그 안에서 상태를 건드리면 로딩이 끝난 화면을 뒤에서 바꾼다
- 로딩 중에 리스트를 미리 비우지 않고, 요청에 번호를 매겨 최신 응답만 반영하는 것으로 고쳤다
- 마지막 입력만 필요하다면 throttle보다 debounce다
